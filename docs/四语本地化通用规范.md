# STS2 四语本地化通用规范

适用语言：简体中文 `zhs`、英语 `eng`、日语 `jpn`、韩语 `kor`。供模组卡牌、遗物、药水、状态、事件、怪物和界面文案复用。维护作者：Natsuki。

## 1. 使用范围与证据等级

本规范依据本机游戏 **v0.111.0 / commit `41cef1ea`** 核对，检查日期为 2026-09-07；2026-09-27 在同一版本上补充了模组表的加载与回退、选牌提示、Power 动态变量和常用句式（源表 SHA-256 与快照一致）。它不是官方发布的四语风格指南；游戏自带文档明确规定技术约束，语言风格则归纳自同版本原版文本。

全文使用以下标记：

- **[官方要求]**：游戏 PCK 内 `localization/README.md` 明确写出的规则。
- **[原版惯例]**：同版本四语 JSON 中可直接对照的用词与句式，不表示所有条目都完全一致。
- **[运行时契约]**：本机该版本 `sts2.dll` 中实际的文本构造和格式化行为。
- **[项目实测]**：在本工作区某个模组里实际渲染验证过的写法，注明模组与版本。
- **[项目规范]**：为本工作区复用而制定的制作与验收要求。

配套文件：

- [四语术语表](localization/四语术语表.tsv)：以游戏表名和键为身份，供翻译、表格软件和脚本读取。
- [来源与例句快照](localization/来源与例句.json)：保留版本、原始条目、术语出处及源表 SHA-256，供版本升级后复核。

优先级：**实际效果与格式化上下文 → 目标版本官方术语 → 同类原版句式 → 本文项目风格建议**。发现英文基准与代码不符，先记录并修正基准，不能把错误同步成四种语言。

用户最新确认的机制优先于旧设计稿；代码与最新要求不符时记录差异，不把旧实现当成已确认设计。以下玩家文案分工为 **[项目规范]**，吸收了 Ricardo 的卡面、追击提示与事件制作经验，不把该角色的具体阈值、次数或重置规则推广到其他模组。

## 2. 文件、键名与语言代码

**[官方要求]** 游戏使用以下目录代码；英文是源语言，JSON 为字符串键到字符串值的映射。

| 语言 | 游戏资源目录 | 本规范中的角色 |
| --- | --- | --- |
| 简体中文 | `localization/zhs/` | 中文目标文本 |
| 英语 | `localization/eng/` | 技术结构与键名基准 |
| 日语 | `localization/jpn/` | 日文目标文本 |
| 韩语 | `localization/kor/` | 韩文目标文本 |

**[项目规范]**

1. 只翻译 value，不翻译表名、key、模型 ID、变量名、formatter 名、资源路径。`MY_MOD_CARD.description`、`Damage` 的大小写也属于契约。
2. 四语同表的项目自有 key 集合必须一致。新增、删除、改义时同步处理；没有译完的内容不能凭英文回退就标记“已完成”。删除前检查引用，不能借翻译更改存档身份。
3. 文件采用 UTF-8、标准 JSON、统一缩进；不得有重复 key、注释或末尾多余逗号。默认 JSON 读取器可能静默覆盖重复 key，检查时应显式报告。
4. 游戏目录代码不等于操作系统 locale 或翻译平台代码。不要自行把 `jpn` 改成 `ja`、把 `zhs` 改成 `zh_CN`；模组配置页面或框架若另有语言映射，核对其接口。
5. `assets/localization/` 是常见工程布局，不是所有加载器唯一合法路径。沿用目标模组实际注册、合并和打包路径；新增普通文本不代表设置界面也会自动读取。
6. 模组自有内容按项目命名空间区分；不因省事覆盖原版同名 key。

**[运行时契约]** 模组表的加载方式（`LocManager.LoadTablesFromPath`、`ModManager.GetModdedLocTables`）：

1. 游戏只认 16 个语言代码：`eng`、`zhs`、`zht`、`deu`、`esp`、`fra`、`ind`、`ita`、`jpn`、`kor`、`pol`、`ptb`、`rus`、`spa`、`tha`、`tur`。当前语言取设置里的 `language`；首次启动时按平台语言映射。
2. 游戏逐个遍历原版 `res://localization/<语言>/` 下的表文件，再对每张表查找 `res://<manifest id>/localization/<语言>/<同名文件>` 并合并。由此：
   - 原版没有的表名（自定义表）不会被读取。
   - 不在上表里的目录名不会被读取，例如 `zh_Hans_JP`、`zh_CN`、`ja`，它们是系统区域或翻译平台的写法。RitsuLib 设置界面的自带翻译另走 `localization/settings/<区域>.json`，与游戏表无关，不能拿来证明模组表目录有效。
3. 除英语外，每张表都以英文表为回退，而英文表已经合并了各模组的英文。模组缺某个键或缺整种语言时，玩家看到的是模组的英文。
   - 英文表必须是真正的英文：把中文复制进 `eng`，其余 15 种语言的玩家都会看到中文。
   - 只做了 `zhs` 的模组，`zht` 玩家看到的是英文，不会看到简体中文。
4. 模型文本的键是模型 ID 的条目部分（大写 slug）加后缀，例如 `MY_MOD_CARD_STAR_TRAIL.description`。

原版当前快照每种语言各有 46 个顶层 JSON；英文 7028 项，中文/日文各 6937 项，韩文 6935 项。**这些数字只说明原版快照存在键数差异，不构成模组允许漏译的标准。** 未纳入补丁说明目录。

## 3. 四语都不能改变的内容

**[项目规范]** 翻译前为每个效果核对下列信息，四语必须表达同一组事实。

| 核对项 | 必须区分的内容 |
| --- | --- |
| 主体和目标 | 自己、状态拥有者、施加者、另一名玩家、所有玩家、单个敌人、所有敌人、随机目标 |
| 触发时间 | 战斗开始、你的回合开始/结束、每次打牌、首次、每累计 N 次、下回合 |
| 操作性质 | 造成伤害 / 失去生命；获得 / 施加；抽牌 / 放入手牌；打出 / 生成 |
| 数量关系 | 基础数量、追加数量、次数、层数、上限、每层、剩余数量、概率 |
| 持续范围 | 本次结算、本回合、下回合、本场战斗、整局；永久变化是否写入牌组 |
| 卡牌去向 | 手牌、抽牌堆、弃牌堆、消耗牌堆、永久牌组 |
| 限制与例外 | 至多、恰好、首次、仅、不能、如果、否则、不包含自身 |

不能把“每打出 3 张牌”缩成“打出 3 张牌时”，也不能把“另一名玩家”泛化为“友方”。联机文本应明确拥有者和施加者，避免四语都写“你”却各指不同对象。

中文可以先用于确认设计，但最终应建立完整英文结构基准。英文只是技术比对基准，不要求中日韩文照搬英语语序。

## 4. 占位符与 SmartFormat

### 4.1 必须保留的技术结构

**[官方要求]** 保留占位变量，确保 SmartFormat 合法；官方验证还检查部分上下文中的数字。

**[项目规范]**

- `{Damage}`、`{Damage:diff()}`、`{0}`、`{OwnerName}` 是格式化表达式，不能翻译变量名、改大小写或换成全角括号。
- `:diff()`、`:show:`、`:plural:`、`:choose(...)`、`:cond:` 等语法不是正文；只翻译分支内的人类可读文本。
- 保留 selector 路径、嵌套层级、条件含义和分支顺序。`{ApplierName.StringValue:cond:...|...}` 中的 `.StringValue` 不能删。
- 每个变量都必须由对应模型或显示调用点提供。不能因为名字看起来合理就写 `{Strength}`；实际注册的名字可能是 `{StrengthPower}`。
- 不能将动态变量替换成当前看到的数值；不能把仍会被升级、状态或目标影响的数值写死。
- 四语按**同一表、同一 key**核对。不能要求一个 Power 的 `.description` 与 `.smartDescription` 具有相同变量集合。
- 不用简单的 `\{[^}]+\}` 正则宣称完成 SmartFormat 验证，它无法正确处理嵌套表达式和分支内的 `{}`。

### 4.2 英语复数的语言差异

**[原版惯例]** `cards.json::POMMEL_STRIKE.description` 的抽牌句为：

| 语言 | 原版句子 |
| --- | --- |
| 英语 | `Draw {Cards:diff()} {Cards:plural:card|cards}.` |
| 简中 | `抽{Cards:diff()}张牌。` |
| 日语 | `カードを{Cards:diff()}枚引く。` |
| 韩语 | `카드를 {Cards:diff()}장 뽑습니다.` |

因此，“保留变量”不等于“四语占位符字符串及出现次数完全相同”。中日韩不需要英语的 `card/cards` 语法分支，但数量仍由 `Cards` 提供。

**[项目规范]** 默认先保留英文结构。确需省去纯语法性复数分支时，记录为明确例外，证明数量和含义仍完整。不得以此删除 `IfUpgraded`、`InCombat`、多人目标或有玩法差异的条件分支。若当前校验器严格要求复数 formatter 保留，可使用两支同义的本地化文本，或在项目校验器中设置可审查的同键例外；不要全局关闭变量检查。

### 4.3 升级、条件与图标

| 写法 | 用法和边界 |
| --- | --- |
| `{Damage:diff()}` / `{Block:diff()}` | 原版卡牌动态数值常用写法；保留升级/预览能力，不自行统一改成裸变量 |
| `{IfUpgraded:show:升级文本\|未升级文本}` | 先升级分支，再未升级分支；这里的反斜杠仅为 Markdown 表格转义，实际 JSON 不加反斜杠 |
| `{InCombat:战斗内文本\|}` | 根据上下文显示附加信息；不要把分支中的换行和内部变量移到无条件正文 |
| `{Energy:energyIcons()}` | 原版能量图标 formatter；新建内容要有对应可接受的数值上下文，通常使用 `EnergyVar` |
| `{Stars:starIcons()}` | 原版辉星图标 formatter；新建内容通常使用 `StarsVar`，变量名须与注册一致 |
| `{singleStarIcon}` / `{energyPrefix:energyIcons(1)}` | 依赖调用点注入的图标/前缀上下文，不保证任意自定义 UI 都有这些变量 |
| `{Amount:plural:a card\|[blue]{}[/blue] cards}` | 分支里的 `{}` 代表当前值；原版 `card_selection.json::TO_EXHAUST` 英文用这种写法，单数时整句写成 “a card” |
| `{Amount:choose(1):\|[blue]{}[/blue]장}` | `choose` 可以按数值选分支；原版韩文 `TO_EXHAUST` 用它在数量为 1 时省略量词 |
| `{Nth:choose(1\|2\|3):st\|nd\|rd\|th}` | 英文序数（3rd、4th）。**[项目实测]** 宿星&纳斯在 v0.111.0 上对卡牌变量和 Power 自定义变量都渲染正确。只匹配 1、2、3，21 会显示成 21th，数值可能超过 20 时改写句式 |

**[运行时契约]** `ShowIfUpgradedFormatter` 在升级预览中给所选分支整体加绿色。项目文本只把变化片段放入 `show`，避免整句不变内容也被染绿。原版 `BEGONE.description` 使用如下结构：

```text
[gold]{IfUpgraded:show:Minion Strike+|Minion Strike}[/gold]
```

不要把上述展示格式直接当成 JSON 文件内容；写入 JSON 时换行、引号和反斜杠要使用 JSON 转义。原版已有多种合法图标入参，不能把“所有图标都必须叫 Energy/Stars”设为硬规则。

## 5. 富文本、强调与换行

**[官方要求]** 翻译使用与英文相同的 BBCode 标签，不能增加或删去标签；例如英文的一对 `[b]...[/b]` 在译文中仍须为一对。

**[项目规范]**

1. 保留标签种类、数量、参数、成对关系和强调对象。可以按目标语言语序移动完整语义片段；不要求不同语言的所有标签在句子中保持同一线性顺序。
2. 标签正确嵌套，按逆序关闭，例如 `[sine][red]文字[/red][/sine]`。遇到原版个别不闭合的条目，记录问题，不把它当新文本模板。
3. 常用关键词沿用 `[gold]`。`[blue]` 常见于状态实时数字，`[red]` 常见于危险信息；具体颜色保留英文基准，不由译者凭喜好改色。
4. `[b]`、`[i]`、`[color=X]`、`[gold]`、`[purple]`、`[jitter]`、`[sine]` 属于 README 明示示例；其他标签先查目标版本原版和渲染控件。引擎认识某个标签不代表所有游戏 UI 都会正确显示它。
5. 不把 BBCode 改成 HTML。`<br>` 在少量原版界面文本中存在，但普通描述优先用 JSON 的 `\n`；人物对白中的尖括号内容可能只是文字。
6. 原始 JSON 中使用 `\n` 表示换行，避免误写 `\\n` 导致屏幕上出现字面量反斜杠。按效果段落换行，不按中文长度给四语强制切相同字符数。
7. 不把 `[E]`、Emoji 或自行写的资源路径当通用能量/辉星图标。
8. 名称、按钮、短标题通常不加句号；完整效果句按对应语言加句末标点。不要把标点移进 formatter 的控制语法。

## 6. 四种语言的写作规则

本节为**[原版惯例] + [项目规范]**，不是官方逐语言编辑手册。

| 项目 | 简体中文 `zhs` | 英语 `eng` | 日语 `jpn` | 韩语 `kor` |
| --- | --- | --- | --- | --- |
| 效果句风格 | 短句，常省略显然的主语 | 动词起句：Deal / Gain / Apply / Draw | 简洁常体：与える、得る、付与する、引く | 原版效果常用正式说明体：줍니다、얻습니다、부여합니다、뽑습니다 |
| 数量 | `造成{Damage:diff()}点伤害`、`抽{Cards:diff()}张牌` | 数字与普通单词间留空格，按数量检查单复数 | `{Damage:diff()}ダメージ`、`カードを{Cards:diff()}枚` | `피해를 {Damage:diff()}`、`카드를 {Cards:diff()}장`，保留自然分词 |
| 句末 | `。` | `.` | `。` | `.` |
| 术语与空格 | 不在汉字与数值间机械加空格 | 关键词大小写遵循原版，普通 damage 不因强调一律大写 | 不按英文插入词间空格；助词在高亮名词外 | 助词通常接高亮名词之后，不机械给助词前加空格 |
| 数量修饰 | 点、层、张、次按对象区分 | card/cards、time/times 等语法一致 | 枚、回、体等助数词按对象使用 | 장、번、턴等按对象使用，不能把所有量都翻成“层” |
| 禁止的简化 | 不能混淆中毒/伤害、丢弃/消耗 | 不省略 another、ALL、additional、up to 等范围词 | 不能把弱体与脱力互换 | 不能把 취약、약화、손상 混用 |

补充：

- **简中**：效果正文沿用“造成、获得、给予、失去、抽、打出”等原版动词；避免“进行造成伤害”等冗余表达。名称与设定文字可有风格，但不能侵入规则解释。
- **英语**：不要默认所有可变数值都永远大于 1；卡牌数可能为 1 的文本检查复数分支。标题大小写优先参考同类原版名称，效果句不写成标题式大小写。
- **日语**：规则正文保持常体一致，避免混入中文语序或任意切换成「です・ます」。对白按人物身份保留敬体、口癖和语气；规则正文的常体要求不覆盖对白。
- **韩语**：固定词选正确助词，例如 `[gold]방어도[/gold]를`、`[gold]취약[/gold]을`。动态姓名无法预知收音时，原版 `ADAPTABLE_POWER.smartDescription` 有 `[gold]{OwnerName}[/gold](은)는` 的写法；可参考该语境或改写句式，不能假定存在自动助词 formatter。
- **四语共同**：按钮、标题、效果、背景故事、对白分开处理。不能为了统一规则句式，把角色对白改成说明书口吻。

### 6.1 常用句式四语对照

**[原版惯例]** 同表同键原文，写新效果前先找最接近的一句。句中变量名以原键为准，表格里的 `|` 已转义。

| 用途 | 原版键 | eng | zhs | jpn | kor |
| --- | --- | --- | --- | --- | --- |
| 条件 | `cards::GO_FOR_THE_EYES.description` | If the enemy intends to attack, apply {WeakPower:diff()} [gold]Weak[/gold]. | 如果敌人的意图是攻击，则给予{WeakPower:diff()}层[gold]虚弱[/gold]。 | 敵が攻撃を予定している場合、[gold]脱力[/gold]{WeakPower:diff()}を付与する。 | 적이 공격할 의도가 있다면 [gold]약화[/gold]를 {WeakPower:diff()} 부여합니다. |
| 回合开始、全体 | `cards::NOXIOUS_FUMES.description` | At the start of your turn, apply {PoisonPerTurn:diff()} [gold]Poison[/gold] to ALL enemies. | 在你的回合开始时，给予所有敌人{PoisonPerTurn:diff()}层[gold]中毒[/gold]。 | ターン開始時、すべての敵に[gold]毒[/gold]{PoisonPerTurn:diff()}を付与する。 | 내 턴 시작 시, 모든 적에게 [gold]중독[/gold]을 {PoisonPerTurn:diff()} 부여합니다. |
| 触发 | `cards::VICIOUS.description` | Whenever you apply [gold]Vulnerable[/gold], draw {Cards:diff()} {Cards:plural:card\|cards}. | 每当你给予[gold]易伤[/gold]时，抽{Cards:diff()}张牌。 | [gold]弱体[/gold]を付与するたび、カードを{Cards:diff()}枚引く。 | [gold]취약[/gold]을 부여할 때마다, 카드를 {Cards:diff()}장 뽑습니다. |

## 8. 显示场景的额外规则

### 8.1 卡牌

**[运行时契约]** `CardModel.GetDescriptionForPile` 注入动态变量、升级和战斗上下文，并依据关键词集合与显示规则追加关键词文本。

**[项目规范]**

- 先检查 `CanonicalKeywords` 及实际关键词来源。已经由标准卡牌渲染流程自动显示的“保留、消耗、固有”等，不在 `.description` 再单独重复一行。
- 描述“让另一张牌获得保留”或“消耗手牌”仍需写出对应效果，这与重复本卡固有关键词不同。
- 自定义条件如斩杀，以及没有被自动附加的机制，仍要完整描述。
- 普通卡面、升级卡面、升级预览、战斗外图鉴、选中目标时的数值，都可能使用不同上下文；不能只看 JSON 判定全部显示正确。

**选牌提示**

- **[运行时契约]** `CardModel.SelectionScreenPrompt` 读取 `<卡>.selectionScreenPrompt`，键不存在时直接抛 `InvalidOperationException`。`PowerModel` 的同名属性也一样。`CardSelectorPrefs` 会把可选上限作为 `{Amount}` 注入提示。
- **[原版惯例]** 原版 624 张卡里只有 24 张有 `selectionScreenPrompt`，都写明用途，例如 “选择一张牌放到你的抽牌堆顶。”。消耗、丢弃、附魔、移除、变化、升级这类通用选择用 `card_selection.json` 的 `TO_*` 提示，代码里对应 `CardSelectorPrefs.ExhaustSelectionPrompt` 等静态属性。
- **[项目规范]** 能用原版通用提示的就用；需要本卡专属提示时才写这个键，四语同步写。不给每张卡批量生成“选择卡牌。”一类占位提示。

### 8.2 状态 Power

**[运行时契约]** 本版本的提示入口不同，允许的变量也不同：

| 场景 | 已核实的上下文 | 写作要求 |
| --- | --- | --- |
| `.description` 经 `GetDumbHoverTip` | 通用注入 `Amount`、`singleStarIcon`、`energyPrefix`，不自动加入自定义 `DynamicVars` | 普通引用提示宜解释规则、每层效果，不随意引用实时计数器 |
| `.smartDescription` 经可变实例的 `HoverTips` | 层数、拥有者、多人信息、动态变量；施加者和目标信息按是否存在注入 | 可写当前层数、进度、剩余次数，逐项核对实际提供的变量 |
| `.remoteDescription` | 有对应文本且由其他玩家施加等条件成立时选用 | 如有使用，同步四语并区分“你”和施加者 |
| `HoverTipFactory.FromPower<T>()` | 取规范模型并调用普通提示，可显式传入 amount | 未传数量时通常不是当前战斗实例层数，不能把这里的 `{Amount}` 当实时值 |

**[项目规范]** 不传 amount 的普通引用提示优先用“每层”“等同于层数”等静态规则；实时提示再给当前数字。不能靠删掉智能提示中的变量来掩盖普通提示的上下文错误。`OwnerName`、`TargetName` 等也不能未经核对搬到普通描述。

**[运行时契约]** 智能提示里的 `{Amount}` 是 `PowerModel.Amount`，不是 `DisplayAmount`。图标上显示剩余张数、倒计时的 Power，如果文本里写“还需{Amount}张”，显示的其实是层数。这类数值要用自定义动态变量：

- 动态变量在提示生成的那一刻取值；实例化时从 `CanonicalVars` 克隆，之后不会自动跟随字段变化。要在数值变化处写回 `DynamicVars[名].BaseValue`。
- `AfterCloned` 会清空 `DisplayAmountChanged` 等事件，订阅要放在施加之后（例如 `AfterApplied`）。
- `CanonicalVars` 也会在规范模型（图鉴）上求值，那时没有 Owner，不能在这里读形态或持有者。
- 可参考宿星&纳斯的 `SxPower.DescriptionVars`：子类登记“变量名 → 当前值”，施加、配置和显示数值变化时统一写回。

### 8.3 遗物、药水、事件和 UI

- **[项目规范]** 名称、效果和背景故事分别翻译；名称不承载必要规则，背景故事不能补偿效果描述遗漏。
- **[运行时契约]** `PotionModel` 只读 `title`、`description`、`selectionScreenPrompt`，原版 66 种药水都没有 `.flavor`。药水不写背景故事键；遗物的 `.flavor` 仍然会被读取。
- **[项目规范]** 与原版含义相同的界面文本直接用原版键，各语言由原版提供。例如战后“移除一张牌”的奖励可以用 `gameplay_ui.json::COMBAT_REWARD_CARD_REMOVAL`，不要另起一个只写了中英文的键。
- 事件选项区分玩家行动、消耗、奖励、概率和不可用条件；不能把“有概率获得”译成必定获得。
- 自定义 UI 根据实际控件确认是否支持 BBCode、动态参数和自动换行；不要直接套卡牌上下文。
- 对按钮、长标题和动态姓名预留空间；没有固定的“四语最大字符数”。先保持含义完整，再通过用户实机查看溢出、缺字和换行。

### 8.4 卡面与悬浮提示的分工

以下为 **[项目规范]**，示例是写作模板，不是原版逐字引文。

| 位置 | 承载内容 | 避免的内容 |
| --- | --- | --- |
| 卡牌、遗物效果正文 | 做什么、对谁、多少、何时生效，以及此物独有的条件和例外 | 每张牌重复解释同一个自定义机制 |
| 共享关键词提示 | 机制定义、统计范围、通用次数限制与重置时机 | 某一张牌专属的阈值或升级效果 |
| Power 普通提示 | 每层效果与静态规则 | 无上下文的当前层数或进度 |
| Power 智能提示 | 当前实例的收益、进度和剩余次数 | 尚未获得的能力或无效占位值 |
| 背景故事、对白 | 气氛、人物语气与设定 | 只能从故事中推断的必要规则 |

- **先完整，再精简**：删去“进行”“将会”等不改变含义的赘词；“（向下取整）”、ForcePlay、队列和回调等实现说明通常留在开发文档。若舍入、结算顺序或去向会影响玩家判断，保留必要解释或提供准确数值，不能以“原版风格”为由隐藏规则。不要机械删除全部括号或所有“每回合”。
- **共享规则只解释一次**：多张牌使用同一机制时，卡面写触发阈值和效果，提示写通用定义与限制。迁移后检查玩家能从该卡实际打开提示；独有次数、例外和升级差异仍留在对应卡面。
- **分清三种计数**：累计多少触发、允许触发几次、何时重置，是三个不同事实。特别核对“每张牌”是否指每个实体副本、是否包含自动打出、是否跨回合、统计自己还是友方。用本模组确认的规则填写，不能套用 Ricardo 的数值。
- **同效果同措辞**：对照基础与升级牌、遗物、状态和关键词提示，按“主体—时机—动作—数量—范围”比较。统一“造成伤害、获得格挡、抽牌”等用词；伤害与失去生命、抽牌与加入手牌、每次攻击与每段命中不属于同义替换。
- **高亮不等于提示**：`[gold]关键词[/gold]` 只负责显示颜色。自定义关键词还需在实际显示入口提供相应 hovertip；原版自动显示的卡牌关键词按 8.1 节处理。提示嵌套使用框架已有预览，检查重复与递归。
- **风味文本独立检查**：效果与 `.flavor` 分开维护。实际读取的背景故事键必须存在，不能让遗物详情显示本地化键名；是否留空依项目约定与控件支持决定。

例如，若项目已确认每张追击牌每回合至多自动触发一次，可将卡面写为“友方每打出{Threshold}张攻击牌，追击一次。”，共享提示说明统计是否包含自动打出、免费打出及次数重置规则。这个模板的变量需映射到项目真实变量；若计数保留至下回合，提示必须反映该规则。

### 8.5 事件文案与奖励预览

**[项目规范]** 参考同类原版事件，以及项目已有事件的叙事口吻；其他模组的字体、分辨率、布局和配色属于其自身界面约定，不作为通用硬性要求。

- 正文讲遭遇与人物反应；选项标题写简短行动；选项说明写真实消耗、收益、概率与必要门槛；后续页交代选择结果。机械效果短句与人物对白分别润色，不把对白改成规则说明。
- 遗物替换需同时说明失去与获得，例如“失去理发卷。获得被偷走的理发卷。”；只写获得会掩盖实际代价。锁定选项保留相同动作名称，并说明真正缺少的条件。
- 奖励或代价涉及可预览的卡牌、遗物和状态时，连接相应原生或框架提示；首个选项、后续页和锁定选项分别检查。绑定遗物展示信息与填充 `HoverTips` 不能视作同一件事，需核对目标版本的选项构造路径。
- 气氛正文可沿用项目色彩；效果说明只强调有意义的奖励、代价和关键词，不把叙事的抖动、波浪效果铺满按钮。翻译仍保留已批准基准的标签结构。
- 按语义分段，JSON 中用 `\n\n` 分隔段落，不按某张截图的宽度手工断行。篇幅问题先检查容器和自动换行；未经允许，不靠删台词或缩小字体改写用户定稿。

## 9. 可直接复用的制作流程

1. **确定基准**：记下游戏版本、四语目录、实际加载路径、模型/表/key 及对应效果。
2. **整理词表**：优先查本文 TSV 和目标版本同键原文，补齐项目专名；不凭其他游戏或 STS1 印象替换 STS2 术语。
3. **冻结语义与技术结构**：确认触发时机、对象、数量、持续时间；列出 BBCode、变量、formatter、条件和图标。
4. **完成英文基准与三种译文**：允许自然语序，不改变效果；纯复数结构调整逐键记录。
5. **做静态检查**：严格 JSON、重复键、四语同键覆盖、标签、变量与分支、术语和数值。
   文案由脚本或内容表生成时，先改权威来源再生成；同时查基础/升级文本、共享提示和实际支持的语言目录，不能只改输出 JSON。共享规则迁移到提示后，核对对应模型和选项的提示连接。
   这些检查宜做成构建步骤。可参照宿星&纳斯的 `tools/check_localization.py` 与 `generate_content.py`：
   - 译文按条目叠加在中文源上，缺译或多出条目时生成器直接中止。
   - 生成后逐键比对各语言的键集合、占位符变量名集合（不比出现次数，见 4.2）和各标签数量。
   - 检查只有游戏认识的语言目录、英文表里没有汉字。
   - 用正则拦截 6.2 节的少用写法。
   - 加检查后做一次反向测试：故意删一条译文、改坏一个标签，确认会失败。
6. **按交付范围检查资源**：需要发行包时再打包并检查实际包含的四语文件；只改本规范等文档时，仅查差异和引用，不启动游戏。
   发行或部署文案修复时，对比包内本地化与当前生成结果；源码改对、DLL 更新不代表 PCK 文案已更新。源语言回退或复制中文到其他语言目录不算完成翻译。
7. **渲染检查按语言分别做**：静态检查看不出 `plural`、`choose`、动态变量能否解析、选中了哪个分支。可以在隔离的游戏副本里渲染卡牌描述和 Power 提示，并检查有没有残留的 `{`。
   - 游戏语言取自 `settings.save` 的 `language`，只有当前语言会被渲染。每种语言要在各自的隔离 HOME 里改这个值再跑一次。
   - 隔离运行要带 `--force-steam=off`，不改用户真实的设置和存档。
8. **由用户完成实机复核**：如用户保留实机测试权，交付待看场景及已验证层级，不替用户启动游戏或修改其真实语言设置。

### 查原版文本

原版本地化在游戏 PCK 里，不在磁盘上。rich-text 技能的扫描脚本能直接解析 PCK：

```bash
python3 ~/.claude/skills/sts2-rich-text-tags/scripts/scan_sts2_rich_text.py --language all
```

脚本里的 `resolve_pck`、`read_pck_entries`、`read_entry` 可以导入，把 `localization/**/*.json` 原样写到临时目录。之后按短语统计出现次数、按同一个键对照四语，就能判断某种写法是不是原版惯例。写出的文件可用配套 JSON 里的 `source_table_sha256` 确认与快照同版本。

### 更新原则
